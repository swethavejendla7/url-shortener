# AI Traceability Log

This log records how AI assistance was used across the build: what was asked for, what the AI
produced, and whether the engineer accepted it as-is, edited it, or rejected it — with the
reasoning behind that call. It exists because "AI wrote it" is not itself a quality signal; the
review decision is. Entries are grouped by scenario, in build order.

Legend: **Accepted** = used as generated · **Edited** = generated output changed before use ·
**Rejected** = generated output discarded, different approach taken.

## Scenario 1 — Greenfield

| # | Task / intent given to the AI | What was generated | Review outcome | Rationale |
|---|---|---|---|---|
| 1 | Scaffold `package.json`, `tsconfig.json`, ESLint config for a TS/Express/SQLite service | Standard config files | **Accepted** | Boilerplate; matched conventions, nothing project-specific to get wrong |
| 2 | Build a repository/service/controller layering for URL CRUD, following the schema and constraints already agreed (base62 codes, soft delete, optional expiry) | `urls.repository.ts`, `urls.service.ts`, `urls.controller.ts` | **Accepted**, with one deliberate design note kept in-code | The repository's `create()` intentionally uses a check-then-insert pattern rather than an atomic upsert. This was a conscious choice, not an oversight — it's a realistic bug to demonstrate finding and fixing in the brownfield scenario. Documented inline as a `NOTE` comment and in `01-greenfield.md` rather than silently shipped |
| 3 | Add structured request logging via `pino-http` | `import pinoHttp from 'pino-http'; app.use(pinoHttp({ logger }))` | **Rejected → edited** | Failed `tsc --noEmit`: `pino-http`'s default export has no call signature under `NodeNext` module resolution. Root-caused by reading the package's `.d.ts` directly (`export default PinoHttp; export { PinoHttp as pinoHttp };`) rather than suppressing the type error. Switched to the named `pinoHttp` export |
| 4 | Redirect endpoint: resolve short code, log the click, send the redirect | Initial draft used `res.redirect(...)` immediately and logged the click asynchronously afterward ("fire and forget") to minimize perceived latency | **Rejected → edited** | `better-sqlite3` is a synchronous API; "fire and forget" here just means an unhandled promise-shaped footgun for no real benefit, and a process crash between the response and the write would silently drop the click. Changed to record the click synchronously *before* sending the redirect. The latency cost is sub-millisecond (SQLite insert vs. network redirect), not worth trading away durability for |
| 5 | Write an integration-test harness against an isolated DB per test | First draft set `process.env.DB_PATH = ':memory:'` as the first statement in the test file, before its `import` lines | **Rejected → edited** | Looked correct, was not: ES module `import` statements are hoisted above ordinary statements in the same file, so the app's config module read the *pre-override* `DB_PATH` before the assignment executed. Caught by noticing an unexpected `data/shortener.sqlite` file on disk after running the suite — the tests still passed, which is precisely why this needed to be caught by inspection rather than trusted because "tests are green." Fixed by moving env setup into a Vitest `setupFiles` entry, which is guaranteed to run before any test file's own module graph loads |
| 6 | `npm install`'s dependency scripts (`better-sqlite3` native build, `esbuild` binary fetch, `fsevents` for file watching) | npm's install-script gate flagged these as pending approval | **Reviewed, then approved** | All three are well-known, widely used packages (better-sqlite3's native binding, esbuild's platform binary, fsevents' macOS file-watching backend) performing their standard, expected install-time behavior — not blindly approved, but not treated as equally risky as an unfamiliar package requesting install scripts would be |

## Scenario 2 — Brownfield

| # | Task / intent given to the AI | What was generated | Review outcome | Rationale |
|---|---|---|---|---|
| 1 | Confirm whether the greenfield check-then-insert pattern is actually exploitable via concurrent HTTP requests before fixing it | Initial instinct was to jump straight to "yes it's racy, add a retry" | **Rejected → investigated first** | Traced the call path and confirmed `better-sqlite3` is synchronous with no `await` between the `SELECT` and `INSERT`, so Node's run-to-completion model means concurrent *requests to one process* cannot interleave there. Fixing a non-existent single-process race for the wrong stated reason would have undermined the whole scenario's credibility |
| 2 | Design a way to prove the *real* exposure (multi-process interleaving) without flaky, timing-dependent tests | First idea: `Promise.all` of concurrent `fetch` calls against a running server | **Rejected → redesigned** | With a synchronous DB driver, concurrent `fetch` calls would just create N distinct random codes and prove nothing about the vulnerable gap. Replaced with driving the two low-level SQL statements directly in the exact interleaved order genuine multi-process contention would produce — deterministic, not timing-dependent |
| 3 | Fix `UrlsRepository.create()` to be atomic | Removed the `SELECT` pre-check; `INSERT` directly, catch `SQLITE_CONSTRAINT_UNIQUE`, translate to `ShortCodeTakenError` | **Accepted** | Matched the intended design; also incidentally removes one DB round-trip per create call |
| 4 | Add per-IP rate limiting to the create and redirect endpoints via `express-rate-limit` | Module-level singleton limiter instances imported into the router | **Rejected → edited**, caught by a failing test | The second rate-limit integration test failed with an unexpected 429 on its very first request. Root cause: singleton limiter instances retain hit counts for the process lifetime, so sequential test cases in the same file (each building a "fresh" app) were silently sharing one exhausted counter. Refactored `rateLimiter.ts` to export factory functions so every `createApp()` call gets its own limiter state — this is also better production design (no hidden cross-instance coupling), not just a test-only fix |
| 5 | Regression tests for the atomic-insert fix and the retry/exhaustion paths | Tests using `vi.mock` on the short-code generator module to force deterministic collisions | **Accepted, with one correction mid-draft** | An earlier draft tried `vi.spyOn` directly on the imported module namespace object; kept the cleaner, more reliable `vi.mock(..., importOriginal)` hoisted-mock pattern instead once both were compared, since it's the documented-supported approach for mocking a single named export from an ESM module in Vitest |

## Post-build review — cache-invalidation bug found by manual smoke test

| # | Task / intent given to the AI | What was generated | Review outcome | Rationale |
|---|---|---|---|---|
| 1 | Run a full manual smoke test against a real running server as the final validation pass, beyond the automated suite | Sequence: create a link, redirect through it (to warm the redirect cache), soft-delete it, then request the redirect again | **Bug found, not "generated"** | The final redirect returned `302` to the original target instead of `410` — despite the DB row showing `is_active = 0`, confirmed directly via `sqlite3`. All 48 automated tests were passing at this point; none of them happened to redirect through a link *before* deleting it, so none exercised this path |
| 2 | Root-cause the discrepancy between "DB says deleted" and "endpoint says still active" | Traced `app.ts`: `UrlsController` (mounted under `/api/urls`) and `RedirectController` (mounted at `/:shortCode`) were each constructed with their own default `new UrlsService()` — two independent instances, each owning its own `TtlCache`. `UrlsService.delete()` only invalidates the cache on *its own* instance | **Confirmed as root cause** | `DELETE` went through the `/api/urls` controller's `UrlsService`/cache; the redirect read from a *different* `UrlsService`/cache that was never told about the deletion and kept serving the pre-delete cached record until its 5-minute TTL expired |
| 3 | Fix the composition so both controllers observe the same cache | Construct a single `UrlsService` in `app.ts` (the composition root) and inject it into both `UrlsController` and `RedirectController`, rather than letting each fall back to its own default instance | **Accepted** | Both constructors already supported dependency injection (`private readonly service: UrlsService = new UrlsService()`); the bug was only in how `app.ts` wired them, not in either controller or in `UrlsService` itself — no service-layer changes needed |
| 4 | Add a regression test for this specific sequence | New test in `tests/integration/urls.api.test.ts`: create → redirect once (warm the cache) → delete → redirect again, asserting `410` | **Accepted** | The existing "returns 410 for a deactivated link" test doesn't redirect before deleting, so it structurally can't catch this — a passing test suite was not, by itself, evidence this class of bug was covered |

This is called out separately from the three scenario tables above because it wasn't part of executing a planned task — it's what the "Validation and Risk Control" step of the process is actually for: the bug existed in already-committed, already-tested, already-passing code, and manual smoke testing against a real server (not just the automated suite) is what surfaced it. See `ENGINEERING_SUMMARY.md`'s risk table for the consolidated entry.
